## Роль

Геракл — не разовый «удали вот это». Это протокол периодической уборки нескольких мест, которые
незаметно захламляются между чистками: два «мозга» (LightRAG + Obsidian-каталоги студентов),
установленные скиллы, файлы самого проекта, живые/мёртвые API-ключи по всему проекту, и очередь
уроков/паттернов, которая копится, но сама себя не разбирает. Раз в цикл («субботник») Геракл
проходит по всем зонам, находит кандидатов,
показывает владельцу проверяемое доказательство — и только после этого действует.

## Правило №0 — журнал отката, ДО первого действия

**Первое, что создаётся при запуске скилла, — журнал шагов. Раньше любой команды, меняющей состояние.**
Файл: `<системная папка>/logs/LOG_ШАГОВ_<YYYY-MM-DD>.md` (для субботника вне переезда — рядом с отчётом
субботника). Каждое действие записывается **сразу после выполнения**, не пачкой в конце:

| # | Время | Что сделал (точная команда) | Зачем | Откат (точная команда) |
|---|---|---|---|---|

- «Меняет состояние» — это не только удаление: остановка контейнера/сервиса, смена restart-политики,
  правило ufw, правка конфига, перенос файла, запись в БД. Всё это — строка в журнал.
- **Исходное значение снимать ДО изменения** (`docker inspect … RestartPolicy`, `ufw status numbered`,
  `systemctl is-enabled`, копия конфига), чтобы в колонке «Откат» стояло реальное прежнее значение,
  а не догадка.
- Только чтение (опись, дамп, проверка ключа) — тоже строка, откат «не нужен». Так видно полную хронологию.
- Делегируешь шаг субагенту — требование журнала передаётся в его промпт, его действия попадают в тот же файл.

## Первый принцип — прежде всех остальных

**Перед необратимым или широким действием — проверяемое доказательство, не словесное «удалить X?».**

Это не отдельная опция, это то, как Геракл вообще работает. Формулировка владельца (`feedback_ask_before_execute`):
> Перед действием с широким эффектом или необратимым — если можно объективно проверить состояние
> (скриншот, вывод команды, содержимое файла) — просить именно это, а не довольствоваться словесным
> подтверждением.

Применительно к Гераклу это значит: не спрашивать «можно снести N?» в вакууме — показать *что*
нашли и *почему* это кандидат (автор/дата установки/частота использования/грep по CLAUDE.md — см.
`references/checklist.md` и отчёты прошлых субботников за образцами реальных находок). Архивировать
по умолчанию, удалять насовсем — только когда паттерн уже безошибочный (явный битый дубль, пустой
шаблон, мёртвый клон публичного репо) или владелец явно подтвердил после того, как увидел доказательство.

**Не переспрашивать по мелочам, где паттерн уже чёткий** (см. пример: временные файлы `*.tmp`,
файл `(2)`-конфликт синка, дубль с идентичным содержимым) — переспрашивать там, где неочевидно или
цена ошибки высокая (чужие данные клиентов, единственная копия чего-то, ключи/секреты).

## Когда запускать

- владелец говорит «субботник» / «почисти» / «генеральная уборка» без указания на конкретный файл
- Плановый цикл (первый прогон — конец месяца, дальше — по факту, раз в месяц ориентир из БОНУС-7)
- Кто-то из клуба «Нейроренессанс» жалуется на несвязанный/захламлённый Obsidian-vault
- Перед крупной миграцией/переездом (например, перед переездом на Oracle) — чтобы не тащить мусор

9. **Системная папка** (`<системная папка>/` или её аналог; новая зона, 11.11.2026) — папка разрастается
   разовыми отчётами, бэкапами и «общими журналами обо всём». Правила (`references/folder-structure.md`,

     сигнал к уборке.
   - **Тематическое → `kb/`** (`errors/<тема>.md`, `patterns/<тема>.md`, runbook-и). Общий журнал
     «всё обо всём» не вести: разнести по темам, живые записи — в `kb/`, записи про мёртвые
     инструменты — только в архив. Большой файл разбирать внешней моделью, план проверять самому.
   - **Разовое → `logs/`** (отчёты, HANDOFF после закрытия хвостов), журналы переезда серверов —
     `logs/migration/`.
   - **Бэкапы — не в системной папке**: в архив вне git. Копии `.env` и ключей не хранить — удалить
     (по ОК).
   - **Безопасность переноса**: перед тем как приватное (бэкапы, промокоды, журналы с IP) окажется в
     отслеживаемом месте — сначала правило в `.gitignore` + `git check-ignore`, потом перенос. Ключи в
     отслеживаемых файлах — заменить ссылкой на файл секретов. Тяжёлые бинарники (PDF) — проверить,
     что не в git.

     журналы и архив не трогать (это история). Отдельные git-репо внутри — коммитить отдельно.

      память всех проектов) — тоже. Появилась новая исключённая папка или новый каталог настроек —

    - **Ключ расшифровки есть у владельца** (менеджер паролей/флешка) — без него копия бесполезна;
      раз в квартал — пробная расшифровка на его компьютере.

11. **Версии авторских скиллов FreeMind** (новая зона, 26.11.2026) — скиллы обновляются между
    субботниками, а витрина и копии у людей отстают. Два режима:
    - **Автор скиллов:** `python3 <инструменты>/skills-sync/check_versions.py` — таблица
      «рабочая ↔ витрина»: ⬆️ обновить витрину, 🆕 не опубликован, ⚠️ на витрине новее. По каждому
      ⬆️/🆕 — чек-лист `<скиллы>/_БЕЗОПАСНОСТЬ_РАЗДАВАЕМЫХ_СКИЛЛОВ.md`, затем

    - **Проверка:** после обновления открыть SKILL.md обновлённого скилла — версия в заставке
      совпадает с `versions.json`.

## Workflow одного субботника

1. Пройти все 5 зон по `references/checklist.md`, собрать находки — не действовать по ходу сбора.
2. Для каждой находки отметить: зона, что именно, почему кандидат (конкретный признак, не
   ощущение), предлагаемое действие (архив/удаление/слияние/перенос), обратимость.
3. Показать владельцу список одним заходом — сгруппированным по зонам, с доказательством по каждому
   пункту (вывод команды/grep/дата), не пересказом на словах. **Формат отчёта — всегда в два слоя
   (правило от 05.10.2026, первый прогон): сверху короткий отчёт (что нашли, что критично, что
   решать прямо сейчас — несколько строк), под ним сразу полный отчёт (все находки по зонам с
   доказательствами). Короткий — для среза/решения на ходу, полный — для аналитики и разбора потом.
   Делать так при КАЖДОМ субботнике, не только по запросу.**
4. Дождаться ОК по неочевидным/необратимым пунктам. Явные дубли/мусор можно чистить сразу, отметив
   это в отчёте постфактум. Находки уровня «живой секрет/ключ в открытом виде» — эскалировать сразу,
   не дожидаясь, пока соберутся все зоны (это не вопрос уборки, это вопрос безопасности).
5. Действовать — каждый шаг сразу в журнал отката (Правило №0): архив по умолчанию (`<системная папка>/archive/`, или аналог зоны), удаление — только по
   явному подтверждению или бесспорному паттерну.
6. Записать субботник в журнал субботников `history.md` (заводится при первом прогоне) (что почищено, где заархивировано, что перенесено
   живым в канонические файлы) — по образцу трёх прошлых записей уже в файле. Запись тоже в два слоя:
   короткая шапка-итог + полная хронология находок/действий под ней.
