# LightRAG Doctor: техосмотр памяти агента

Инструкция для агента (Claude Code, Cursor или любой, умеющий ходить в HTTP). Человек даст тебе две вещи: адрес сервера LightRAG и API-ключ. Для сверки настроек нужен ещё доступ к серверу, без него шаг 6 пропусти. Дальше работай сам, по шагам ниже.

## Твоя задача

1. Проверить граф по четырём болезням, кеш и настройки сервера.
2. Показать хозяину находки списком, с доказательствами.
3. Починить только то, что он одобрит поимённо.
4. Доказать, что лечение сработало, контрольными вопросами до и после.

Шаги 0 до 6 ничего не меняют в базе и на сервере, только читают. Любая запись начинается после явного согласия хозяина по конкретному списку.

## Правила безопасности

- Не звать `DELETE /documents` ни в каком виде. Это стирает все документы базы. Точка.
- Не писать, пока сервер занят. Перед каждой записью проверь `GET /documents/pipeline_status`. Если `busy: true` или на запись пришёл ответ 409, подожди 30 секунд и повтори. Ответ 503 означает, что сервер восстанавливается после сбоя: остановись и скажи хозяину.
- Перед любой правкой узла сохранить его текущие данные в файл. Восстановить удалённое иначе нельзя.
- Показывать список перед действием. Склейка и удаление необратимы.
- API-ключ держать в переменной окружения. Не печатать его в чат, в отчёт, в файл.
- Не заливать в LightRAG сырые логи, дампы `.env`, SQL и конфиги: из них рождается мусор и утекают секреты.
- Не открывать и не показывать `.env` целиком, не копировать его с сервера: там ключи и пароли. Только строки из шага 6.
- Сомневаешься, осколок это или тёзка: не трогать, вынести в вопросы хозяину. Только он знает, кто есть кто в его базе.

## Шаг 0. Подключение

```bash
export LR_URL="https://lrag.example.ru"
export LR_KEY="<ключ>"
curl -s -H "X-API-Key: $LR_KEY" "$LR_URL/health"
curl -s -H "X-API-Key: $LR_KEY" "$LR_URL/documents/pipeline_status"
```

Из `/health` выпиши `core_version` и настройки реранка, если есть. Версия важна для шага 9:

- 1.5.7 и старше (включая 1.5.4): есть отдельная команда чистки кеша.
- 1.5.8rc1 и новее: команды нет, кеш обходят другими вопросами.

Если `pipeline_status` показывает `busy: true`, не начинай, дождись окончания индексации.

**Сразу сверь версию с актуальной и скажи хозяину в первом же ответе** (правило добавлено после реального техосмотра, где отставание на 7 месяцев заметили только в середине лечения):

```bash
curl -s https://api.github.com/repos/HKUDS/LightRAG/releases?per_page=3 | grep -E '"tag_name"|"published_at"'
docker image inspect <образ> --format '{{.Created}}'   # когда образ реально скачан
```

- Тег `latest` в `docker-compose.yml` не значит «свежая версия»: образ обновляется только по `docker compose pull`. Смотри `core_version` из `/health`, а не тег.
- Отстаёт хотя бы на минорную версию (1.4 → 1.5): **сначала обновление, потом лечение.** В новых версиях другие маршруты API (в 1.4.x удаление узла — `DELETE /documents/delete_entity`, в 1.5 — `/graph/entity/delete`), появились настройки против мусора (`ENTITY_TYPE_PROMPT_FILE`, JSON-извлечение), иначе склеиваются узлы. Лечить на старой версии = делать работу дважды.
- Обновление — только после полного дампа (шаг 0.5), на закреплённый тег (`ghcr.io/hkuds/lightrag:v1.5.8`, не `latest`), затем `docker compose up -d --force-recreate`, проверить `/health`, логи миграции и подключения (MCP, n8n, скрипты, которые ходят в API).
- Решение об обновлении принимает хозяин: показать ему версию сейчас, актуальную, что даст и чем рискует.

Все примеры ниже идут через `curl`, заголовок `X-API-Key` везде.

## Шаг 0.5. Полный дамп базы до любых правок (обязательно)

Бэкапы отдельных узлов из шага 1 не спасут от ошибочной склейки пачкой или удаления не того. Перед шагом 8 сними полную копию хранилища. Без дампа лечение не начинать.

PostgreSQL (в том числе с графом Apache AGE):

```bash
mkdir -p ~/backups/lightrag_$(date +%F) && chmod 700 ~/backups/lightrag_$(date +%F)
docker exec -e PGPASSWORD="<пароль из .env>" <postgres-контейнер> \
  pg_dump -h 127.0.0.1 -U <POSTGRES_USER> -d <POSTGRES_DATABASE> -Fc > ~/backups/lightrag_$(date +%F)/lightrag.dump
docker exec -i <postgres-контейнер> pg_restore -l < ~/backups/lightrag_$(date +%F)/lightrag.dump | grep -c 'TABLE DATA'
```

- Через сокет внутри контейнера часто падает `Peer authentication failed`: подключайся по `-h 127.0.0.1` с паролем.
- Пароль бери из `.env` в переменную, в чат и в файлы не печатай.
- Проверка: файл не пустой, `pg_restore -l` видит таблицы.
- Файловое хранилище (JSON/NetworkX/NanoVectorDB): скопируй целиком папку `rag_storage` (`tar czf`).
- Дамп содержит всё, включая секреты, если они попали в граф: права 600, не в git, не скачивать на чужие машины.

Откат при беде: `pg_restore --clean -d <база>` из этого файла, затем пересоздать контейнер LightRAG.

## Почему граф болеет (одна минута теории)

LightRAG сливает сущности в один узел по единственному признаку: точное совпадение строки имени. Не по смыслу, не по эмбеддингам, не по «похожести». Регистр и знаки препинания имеют значение: `Qwen` и `qwen` для него два разных узла.

Из этого следуют обе главные болезни:

- одно имя у двух разных объектов, получился один узел с кашей внутри (тёзки);
- один объект под разными именами, получил несколько узлов (осколки).

Сущность здесь это не только человек. Это компания, проект, сервер, скрипт, канал, продукт. Всё, что есть в графе узлом.

Дорогая модель и смена эмбеддинга это не лечат. Лечит ручная склейка и дисциплина имён в документах.

## Шаг 1. Снять весь граф (только чтение)

```bash
mkdir -p lightrag-doctor
curl -s -H "X-API-Key: $LR_KEY" "$LR_URL/graph/label/list" > lightrag-doctor/labels.json
```

Получишь массив всех имён. Посчитай и запиши общее число сущностей: оно пойдёт в отчёт.

Разведка по одному имени:

```bash
curl -s -H "X-API-Key: $LR_KEY" "$LR_URL/graph/label/search?q=Иван&limit=50"
curl -s -H "X-API-Key: $LR_KEY" --get --data-urlencode "label=Иван Иванов" "$LR_URL/graphs" --data "max_depth=1&max_nodes=50"
```

- `label/search` ищет по подстроке, когда нужно найти все варианты написания.
- `graphs?label=` отдаёт сам узел (описание, тип, `source_id`, файлы-источники) и его связи. Этим ты смотришь на suspect-узел перед любым решением.
- `graph/label/popular?limit=50` отдаёт узлы, отсортированные по числу связей. Самые толстые хабы графа.

Для каждого подозрительного узла сохрани в `lightrag-doctor/` его ответ `graphs?label=`. Это и есть доказательство для отчёта, и бэкап на случай правки.

## Шаг 1.5. Болезнь 0. Секреты в графе (самая опасная, проверять первой)

Что это: экстрактор делает узлами всё, что похоже на имя, в том числе ключи API, токены, пароли, почты и IP из залитых техдокументов. Такой узел может всплыть в ответе любому, у кого есть доступ к базе или к агенту поверх неё.

Как искать. Прогони `labels.json` регулярками, в чат печатай только первые 4 символа и длину, никогда значение:

- ключи: `sk-…`, `sk-proj-…`, `AIza…`, `hf_…`, `ghp_…`, `github_pat_…`, `gsk_…`, `nvapi-…`, `xoxb-…`, JWT `eyJ…`, бот-токены Telegram `цифры:AA…`;
- длинные hex/base64 от 24 символов (пароли, Account ID);
- email, телефоны, IP с портами.

По каждому кандидату открой `graphs?label=` и определи по соседям и описанию, **от какого сервиса ключ** — этот список хозяин получит отдельно: удаление узла не отзывает ключ, отзывать его у провайдера должен хозяин. Короткие префиксы (`sk-proj-oX4Z`) — не целый ключ, но указывают, какой ключ светился.

Как чинить: бэкап узла в файл с правами 600 → удаление (1.4.x: `DELETE /documents/delete_entity`, 1.5.x: `DELETE /graph/entity/delete`).

Подводные камни (проверено на практике):
- **Логи контейнера.** Сервер пишет в журнал имя удаляемого узла целиком (`Entity Delete: remove '<ключ>'`). После чистки секретов пересоздай контейнер (`docker compose up -d --force-recreate`) — старый журнал уйдёт вместе с контейнером. Удобно совместить с обновлением версии.
- **Куски исходных документов.** Удаление узла не трогает текстовые куски (chunks): ключ остаётся в тексте документа-источника и найдётся в режимах `naive`/`mix`. Найди документы-источники (`file_path` узла), почисти исходник от ключей и перезалей документ.
- **Кеш LLM** мог запомнить ответы с ключом: после чистки сбрось кеш (шаг 9).
- **Дамп** (шаг 0.5) содержит секреты — права 600, не в git.
- На большом графе в Apache AGE удаление идёт медленно (минуты на узел, перебор без индекса): запускай фоном, не обрывай.

## Шаг 2. Болезнь 1. Тёзки

Что это: один узел, внутри два разных объекта. Описание превращается в кашу, и каждый ответ по этому имени заражён.

Как искать:

1. Возьми `graph/label/popular?limit=50`. Тёзки почти всегда сидят в хабах: на одно короткое имя сыплются связи всех тёзок.
2. Добавь имена без уточнения: одно слово или «Имя Фамилия» без скобок. Спроси хозяина, какие имена в его базе заведомо повторяются (его собственное, частые имена, название компании).
3. Для каждого кандидата открой `graphs?label=` и прочитай описание и связи.

Признаки тёзки:

- в одном описании факты, которые не могут принадлежать одному объекту: два города, две профессии, два проекта-владельца;
- связи тянутся в разные, не пересекающиеся области графа;
- `source_id` ссылается на документы из разных проектов или клиентов.

Как чинить (API не умеет резать узел, поэтому переносим вручную):

1. Согласуй с хозяином: какое имя у первого объекта, какое у второго, какие связи чьи.
2. Создай узел для второго объекта:

```bash
curl -s -X POST -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" \
  -d '{"entity_name":"Иван Иванов (Логистика)","entity_data":{"entity_type":"PERSON","description":"Логист из проекта Дельта. Отвечает за маршруты.","source_id":"lightrag-doctor"}}' \
  "$LR_URL/graph/entity/create"
```

3. Перенеси его связи. Для каждой связи, которая принадлежит второму объекту: создай такую же от нового узла, старую удали.

```bash
curl -s -X POST -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" \
  -d '{"source_entity":"Иван Иванов (Логистика)","target_entity":"Проект Дельта","relation_data":{"description":"Руководит логистикой проекта","keywords":"логистика, маршруты","weight":1.0,"source_id":"lightrag-doctor"}}' \
  "$LR_URL/graph/relation/create"
curl -s -X DELETE -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" \
  -d '{"source_entity":"Иван Иванов","target_entity":"Проект Дельта"}' \
  "$LR_URL/graph/relation/delete"
```

Следи за направлением: если старый узел в связи был целью, в новой связи он тоже цель.

4. Приведи в порядок основной узел: новое имя с уточнением, чистое описание, правильный тип.

```bash
curl -s -X POST -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" \
  -d '{"entity_name":"Иван Иванов","updated_data":{"entity_name":"Иван Иванов (Стройдом)","entity_type":"PERSON","description":"Владелец компании Стройдом. Клиент с 2025 года."},"allow_rename":true}' \
  "$LR_URL/graph/entity/edit"
```

Важно про `entity/edit`:

- новое имя задаётся в `updated_data.entity_name`, без `"allow_rename": true` сервер его проигнорирует;
- `description` заменяется целиком, а не дописывается. Пиши сразу полное новое описание;
- если новое имя уже занято, сервер ответит 400. Это защита. Не ставь `allow_merge`, чтобы обойти: так ты сольёшь двух разных объектов, то есть вернёшь тёзку обратно.

## Шаг 3. Болезнь 2. Осколки одной сущности

Что это: один объект в документах назвали по-разному, и он разлетелся на несколько узлов. Знания о нём дробятся, ответы получаются урезанными: в контекст попадает один осколок, а не всё.

Как искать. Прогони весь `labels.json` через группировку. В одну группу попадают имена, у которых совпадает:

- написание без регистра и знаков препинания (`Qwen`, `qwen`, `Qwen.`);
- имя плюс инициал или фамилия (`Иван И.`, `Иван Иванов`);
- одна строка содержится в другой (`Клинов`, `Клинов Алексей`);
- имя плюс роль (`Иванов`, `Иванов-владелец`, `Иван (заказчик)`);
- транслитерация (`Сбер`, `Sber`).

Кандидат в осколки это ещё не приговор. По каждой группе открой все узлы через `graphs?label=` и проверь три вещи:

1. Описания не противоречат друг другу (нет разных городов, профессий, владельцев).
2. Соседи по графу пересекаются: связаны с одними и теми же проектами, людьми, компаниями.
3. Хозяин подтвердил, что это один объект.

Все три сошлись: осколки. Хотя бы одно разошлось: вероятно, тёзки, см. шаг 2.

Как чинить. Склейка одна на группу, с уже согласованным целевым именем:

```bash
curl -s -X POST -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" \
  -d '{"entities_to_change":["Иван И.","Иванов-владелец","иван иванов"],"entity_to_change_into":"Иван Иванов (Стройдом)"}' \
  "$LR_URL/graph/entities/merge"
```

Что делает сервер, и что из этого следует:

- все имена в `entities_to_change` должны существовать ровно в том написании, как в графе, иначе 400 с сообщением `Source entity '…' does not exist`;
- связи со всех осколков переносятся на целевой узел;
- описания склеиваются в одну строку через `<SEP>`, а тип берётся от первого в списке. Поэтому сразу после склейки открой `entity/edit` и перепиши описание одним связным текстом, тип поставь правильный;
- целевое имя уже существует в графе: осколки уйдут в этот узел. Проверь до вызова, что это тот самый объект;
- склейку нельзя отменить. Бэкапы узлов из шага 1 должны быть на диске.

Порядок внутри хода: склейка, затем `entity/edit` с новым описанием, затем контроль в `graphs?label=`.

## Шаг 4. Болезнь 3. Мусор

Что это: экстрактор слепил сущностью то, что сущностью не является. Узлы ничего не значат, но засоряют поиск и раздувают граф.

Как искать. Прогони `labels.json` по правилам:

- глаголы и предикаты: «занимается», «используется для», «развернул», «хранится в», «связан с»;
- пути и имена конфигов: начинается с `/`, `~`, `.env`, `docker-compose`, `settings.json`;
- даты и числа: `2026-06-15`, `15.04.2026`, `15000`;
- UUID, IP с портом, команды SQL: `CREATE`, `ALTER`, `DELETE`, одиночные `SELECT`;
- обрывки фраз: одно слово из середины предложения, «и», «который», «необходимо».

Прежде чем счесть узел мусором, открой его через `graphs?label=`. Не мусор, если:

- это реальный объект из области хозяина: сервер, скрипт, продукт, канал, документ;
- у узла есть связи, которые несут смысл (дата связана с событием, путь с сервисом).

Мусор удаляется вместе со всеми своими связями. Удаление необратимо.

Как чинить. Сначала список хозяину, потом удаляй по одному из одобренного списка:

```bash
curl -s -X DELETE -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" \
  -d '{"entity_name":"занимается"}' \
  "$LR_URL/graph/entity/delete"
```

Ответ 404 значит, что имя в базе пишется иначе. В сообщении сервер назовёт верный вариант, возьми его из `labels.json`.

## Шаг 5. Болезнь 4. Мёртвый реранкер

Что это: реранкер переупорядочивает найденные куски перед ответом. На CPU он часто не успевает за таймаут. Система ждёт до таймаута и отвечает без него: минута задержки на каждый запрос, пользы ноль. Хозяин может год не знать, что реранкер ни разу не сработал.

Как искать. Нужны логи сервера (есть доступ по SSH или попроси хозяина выполнить):

```bash
docker logs <lightrag-контейнер> 2>&1 | grep -c "using original chunks"
docker logs <lightrag-контейнер> 2>&1 | grep -E "Rerank func|Worker timeout|Error during reranking" | tail -20
```

- Число больше нуля, и строки с `Worker timeout`: реранкер мёртв. Выпиши значение таймаута из строк, оно пойдёт в отчёт.
- Ноль таких строк: реранкер либо работает, либо выключен. Строка старта `Reranking is enabled: …` в логах покажет, включён ли он.

Без доступа к логам можно измерить эффект реранка на ответ, но не таймауты: один и тот же вопрос в `/query/data` с `"enable_rerank": true` и `false`, сравнить наборы сущностей и кусков.

Как чинить. В `.env` сервера:

```
RERANK_BINDING=null
```

Затем пересоздать контейнер:

```bash
docker compose up -d --force-recreate
```

`docker restart` не перечитывает `.env`. До и после замерь время одного и того же вопроса.

Когда реранкер нужен: база выросла, в ответах пошёл чужой контекст, и есть GPU. На CPU heavy-модели вроде bge-reranker-v2-m3 пережёвывают десяток кусков по 20 секунд и больше. По замерам самих разработчиков LightRAG на тестовой базе реранк в режимах `mix` и `naive` заметно повышает долю релевантных кусков, так что «не нужен навсегда» говорить нельзя: не нужен, пока не работает.

## Шаг 6. Сверить настройки

Через `.env` сервера чинится мёртвый реранкер (шаг 5), и там же живут настройки, от которых зависит, насколько часто граф болеет и насколько точно он отвечает. Сверь их с таблицей. Этот шаг только читает `.env`, правки идут в шаге 8 после «да» хозяина по каждому пункту.

Нужен доступ к серверу по SSH. Если его нет, отдай команду хозяину, пусть пришлёт вывод. Файл `.env` лежит в папке LightRAG, рядом с `docker-compose.yml`. В нём ключи и пароли, поэтому целиком его не открывать. Доставать только эти строки:

```bash
grep -n -E '^(OPENAI_LLM_TEMPERATURE|COSINE_THRESHOLD|CHUNK_SIZE|LLM_MODEL|RERANK_BINDING|SUMMARY_LANGUAGE|ENTITY_TYPE_PROMPT_FILE|ENTITY_EXTRACTION_USE_JSON)=' .env
```

Нет строки в выводе: параметр не задан и работает значение по умолчанию. Это не поломка, но сверь его с таблицей. Умолчания: `COSINE_THRESHOLD` 0.2, `CHUNK_SIZE` 1200, `RERANK_BINDING` null, `SUMMARY_LANGUAGE` English, `ENTITY_EXTRACTION_USE_JSON` false. В версиях 1.5.8 и новее тот же параметр может быть задан с префиксом роли (`EXTRACT_OPENAI_LLM_TEMPERATURE`), расширь поиск, если версия такая.

Числа, на которых остановился автор инструкции (малая база, русский язык):

| Параметр | Значение | Зачем |
|---|---|---|
| `OPENAI_LLM_TEMPERATURE` | 0.1 | извлечение фактов должно быть одинаковым |
| `COSINE_THRESHOLD` | 0.2 | заводской порог поиска; выше 0.4 режет полноту: сущность в базе есть, вопрос её не находит |
| `CHUNK_SIZE` | 1200 | заводской; крупнее чанк, выше шанс, что тёзки склеятся |
| `LLM_MODEL` | класс flash-lite | для запросов достаточно; тёзки и мусор модель не чинит |
| `RERANK_BINDING` | null | если по шагу 5 реранкер мёртв |
| `SUMMARY_LANGUAGE` | Russian | имена сущностей, связей и описания на русском |
| `ENTITY_TYPE_PROMPT_FILE` | задан | профиль с допустимыми типами и примерами; чем уже список типов, тем меньше мусора. Шаблон: `prompts/samples/entity_type_prompt.sample.yml` в репозитории LightRAG |
| `ENTITY_EXTRACTION_USE_JSON` | true | извлечение идёт в JSON, надёжнее, но медленнее |

Как оценивать расхождения:

- Совпало или не задано, а умолчание то же: не трогать.
- `COSINE_THRESHOLD` выше 0.2: флаг в отчёт, это самая частая причина «знаю, но не отвечаю».
- `ENTITY_TYPE_PROMPT_FILE` и `ENTITY_EXTRACTION_USE_JSON` не заданы: предложить, они убавляют мусор, но замедляют индексацию.
- `RERANK_BINDING`: менять только по результату шага 5.
- `LLM_MODEL`: менять только если хозяин сам захочет, это его провайдер и его деньги.
- База большая или не русскоязычная: скажи хозяину, что числа автора могут не подойти. Решение за ним.

Как применять, в шаге 8 и только по одобренным строкам. Сначала копия, потом одна правка на параметр, затем одно пересоздание контейнера на всё:

```bash
cp -p .env .env.bak-$(date +%F)
sed -i -E 's/^OPENAI_LLM_TEMPERATURE=.*/OPENAI_LLM_TEMPERATURE=0.1/' .env
printf '\nSUMMARY_LANGUAGE=Russian\n' >> .env
docker compose up -d --force-recreate
```

- Первая команда меняет строку, которая уже есть. Вторая добавляет параметр, которого не было. Добавляемые строки пиши без пустой строки между ними.
- Копия `.env.bak-<дата>` остаётся на сервере рядом с оригиналом: там те же секреты. Не скачивай её.
- После пересоздания проверь: `grep` из начала шага показывает новые значения, `GET /health` отвечает.
- Переиндексация не нужна: порог поиска действует сразу, остальное влияет на документы, которые зайдут после правки.

## Шаг 7. Отчёт хозяину

Собери в одном сообщении, коротко, списками. Числа без прикрас, ничего не скрывая.

```
Техосмотр LightRAG <адрес без ключа>. Версия <core_version>. Сущностей: <N>.

Болезнь 1. Тёзки: <n> подозрений
- <имя узла>: <что перемешано, одна строка>

Болезнь 2. Осколки: <n> групп
- <имена через запятую> → <предлагаемое имя>

Болезнь 3. Мусор: <n> узлов
- <примеры 10 штук>, остальные в файле lightrag-doctor/junk.txt

Болезнь 4. Реранкер: <работает / мёртв, таймаут X с, мёртвых вызовов Y> / <нет доступа к логам>

Кеш: <версия, чем чистим>

Настройки: <совпало X из 8> / <нет доступа к серверу>
- <параметр>: сейчас <значение или «не задано»>, рекомендую <значение>. <зачем, одна строка>

Вопросы к тебе: <что уточнить, кто есть кто>

Жду: какие пункты делать. Без твоего «да» по списку ничего не трогаю.
```

Остановись и жди ответа. Не начинай лечение по своей инициативе.

## Шаг 8. Лечение

Порядок, в котором чинить (уточнён на реальном техосмотре 25.11.2026):

0. **Полный дамп** (шаг 0.5). Без него дальше не идти.
1. **Секреты** (шаг 1.5): удалить узлы, хозяину — список, какие ключи отзывать.
2. **Обновление версии**, если отстаёт (шаг 0): свежий дамп → закреплённый тег → пересоздание контейнера. Заодно уходят логи с именами удалённых секретов.
3. **Настройки** (шаг 6): язык описаний, температура, типы сущностей — до склеек, чтобы новые описания сразу писались правильно. Одна правка `.env`, одно пересоздание контейнера.
4. **Оптимизация графа:**
   1. Тёзки (шаг 2), самые вредные: один узел отравляет все ответы по имени.
   2. Осколки (шаг 3), склейка плюс переписанное описание.
   3. Мусор (шаг 4), по одобренному списку.
5. Реранкер (шаг 5), если у хозяина есть доступ к серверу.
6. Кеш (шаг 9) и контрольные вопросы (шаг 10).
7. Источники: почистить и перезалить документы, из которых пришли секреты и мусор, иначе всё вернётся.

Перед каждым действием сверяйся с одобренным списком. После каждого действия читай узел обратно через `graphs?label=` и проверяй результат. Одно действие упало с 409: подожди и повтори, с 400: разбери сообщение, не повторяй вслепую.

В конце выпиши, что сделано, по числам: склеено X групп, разведено Y тёзок, удалено Z узлов, поправлено W настроек.

## Шаг 9. Кеш

LightRAG кеширует готовые ответы. Ключ кеша включает точный текст вопроса, режим и флаг реранка. После правок графа тот же вопрос дословно вернёт старый ответ, и покажется, что лечение не помогло.

- Версия 1.5.7 и старше (включая 1.5.4):

```bash
curl -s -X POST -H "X-API-Key: $LR_KEY" -H "Content-Type: application/json" -d '{}' "$LR_URL/documents/clear_cache"
```

- Версия 1.5.8rc1 и новее: маршрут `/documents/clear_cache` удалён. Кеш обходят другими формулировками контрольных вопросов.

Не использовать `DELETE /documents?clear_llm_cache=true`: это стирает все документы, а не только кеш.

## Шаг 10. Проверка результата

До первого изменения возьми у хозяина 5 или 6 контрольных вопросов с ожидаемыми ответами и прогони их через `POST /query` (режим `hybrid`). Ответы сохрани. После всех правок прогони те же вопросы заново, в формулировках, отличающихся от исходных. Прогони и старые формулировки: если старая вернула старый ответ, а новая верный, кеш ещё жив, см. шаг 9.

Полезно смотреть, что вопрос реально достаёт из базы, без генерации ответа: `POST /query/data` покажет сущности, связи и куски, которые попали в контекст. Так видно, попал ли исправленный узел и не лезет ли чужой.

Результат хозяину: вопрос, что было, что стало.

## Чтобы не болело снова

1. Канонические имена. Список имён, под которыми объекты должны жить в графе: люди с уточнением, компании, проекты, серверы. «Иван Иванов (Стройдом)», а не «Иван». Список держи в инструкции агенту, который пишет документы, и в самих документах пиши имена так же.
2. Не перезаливай старые документы без правки имён. Экстрактор вытащит имена из текста, и тёзки с осколками вернутся. Сначала правь текст, потом заливай.
3. Настройки сервера держать как в таблице шага 6. Особенно `SUMMARY_LANGUAGE` для русскоязычной базы и профиль типов сущностей: они убавляют мусор.
4. Мусор лечится моделью, а не промптом. Слабая модель экстракции лепит узлом каждое существительное. Подними модель для роли EXTRACT хотя бы до уровня Qwen, потом уже крутить промпты. Дорогая модель для запросов при этом не обязательна.
5. Что не заливать. Логи, дампы конфигов, SQL, переписки без разметки. Сначала чистый текст, потом база.

Любая правка `.env` вступает в силу только после пересоздания контейнера.

## Чего не делать

- Не сливать разные объекты с одинаковым именем. Склейка тёзок делает только хуже.
- Не удалять и не склеивать без показа списка и «да» хозяина.
- Не менять эмбеддинг-модель и её размерность «для качества»: это отдельная работа и полная переиндексация.
- Не оставлять кеш без внимания после правок: контрольные вопросы задавай в новых формулировках.
- Не трогать сущности, в которых не уверен. Вопрос в список хозяину.
- Не обещать, что правки графа спасут от кривых исходников: старые документы вернут всё обратно.
- Не лезть на сервер менять `.env` без отдельного разрешения: шаги 5 и 6 требуют доступа к серверу, и это решение хозяина.
- Не писать в базу, пока идёт индексация (`pipeline_status.busy: true`).

## История правок инструкции

### 26.11.2026 — как включить профиль типов в 1.5.8 (проверено)
- Файл кладётся в `/app/data/prompts/entity_type/<имя>.yml` внутри контейнера — в docker-compose по умолчанию этой папки нет: добавить том `./prompts:/app/data/prompts:ro`, файл — `./prompts/entity_type/<имя>.yml`.
- `.env`: `ENTITY_TYPE_PROMPT_FILE=<имя>.yml` (только имя, без пути) и `ENTITY_EXTRACTION_USE_JSON=true`.
- В YAML обязательны `entity_types_guidance` (строка) и, при JSON-режиме, `entity_extraction_json_examples` (список строк; без него сервер не стартует извлечение). Формат примера: `{"entities":[{name,type,description}],"relationships":[{source,target,keywords,description}]}`.
- В пример положить «ловушки» (путь, IP, ключ, команда) и показать, что они уходят в описание, а не в узлы. Проверка — тестовый документ с мусором, потом `DELETE /documents/delete_document`.
- Профиль защищает граф, но не куски текста: документ с ключом хранится целиком. Секреты фильтровать до вставки.

### 25.11.2026 — дополнения FreeMind по итогам реального техосмотра (база main, 8448 сущностей, версия 1.4.13)
- **Шаг 0 — сверка версии с актуальной.** Сразу сказать хозяину, если отстаём; при отставании на минорную версию сначала обновление, потом лечение. Тег `latest` ≠ свежая версия. Повод: отставание 1.4.13 → 1.5.8 (7 месяцев) заметили только в середине лечения, а маршрут удаления в 1.4.x другой — первая попытка удаления дала 404.
- **Шаг 0.5 — полный дамп базы** до любых правок (`pg_dump -Fc` через `-h 127.0.0.1`, проверка `pg_restore -l`, права 600). Повод: бэкап отдельных узлов не спасает от ошибочной пачки склеек или удалений.
- **Шаг 1.5 — Болезнь 0: секреты в графе.** В нашей базе нашлось ~15 узлов-ключей (Google, HuggingFace, Pixabay, OmniRoute, n8n JWT, префиксы OpenAI, Account ID Cloudflare), 6 почт, 38 IP. Отдельный список «какие ключи отзывать» для хозяина. Подводные камни: сервер пишет имя удаляемого узла в лог; куски исходных документов с ключами остаются; удаление в AGE — минуты на узел.
- **Шаг 8 — новый порядок:** дамп → секреты → обновление версии (заодно уходят логи с секретами) → настройки → оптимизация (тёзки → осколки → мусор) → кеш и контрольные вопросы → чистка и перезаливка источников.
