# Чек-лист субботника — по зонам

> Пройти зоны по порядку или выборочно (если владелец просит почистить конкретно одну). Внутри зоны —
> сначала собрать находки, потом уже решать что архивировать/удалять (см. первый принцип в SKILL.md).

## Зона 1 — LightRAG

1. Спросить `mcp__lightrag__query_text` (mode: hybrid) по подозрительной теме — «что уже есть про X» —
   ПЕРЕД любым удалением/переписыванием. Не чистить вслепую по одному запросу без контекста.
2. Искать явный дубль фактов: два инсерта про одно и то же решение/факт с разной формулировкой —
   кандидат на слияние (оставить более полную/свежую версию).
3. Искать устаревшее: факт, который явно перестал быть правдой (проект закрыт, решение отменено
   более поздним) — кандидат на удаление/пометку.
4. Прогнать содержимое через пирамиду приоритетов (`feedback_lightrag_rules`):
   - решения и причины (топ) → факты о проектах → предпочтения → документация (низ)
   - НЕ должно быть: сырой код, логи, дампы БД, черновики
   - если что-то из «не должно быть» всё же там — кандидат на удаление сразу, без долгих раздумий
     (паттерн чёткий, можно не переспрашивать)
5. Использовать `mcp__lightrag__get_documents` для просмотра списка перед точечным удалением
   через `mcp__lightrag__delete_document` — по одному, с подтверждением по неочевидным.
6. Помнить: LightRAG — общий граф, используется и клубным изолированным инстансом (`lightrag_club`,
   порт 9622) — не путать два инстанса при чистке, они разные MCP-серверы (`lightrag` vs `lightrag_club`).

## Зона 2 — Obsidian-каталоги (студенты клуба «Нейроренессанс»)

1. Взять путь к vault (свой у каждого студента/проекта, не хардкодить).
2. Запустить `audit-graph.py` (см. `references/obsidian-audit-script.md`) — получить % файлов-сирот.
3. Ориентир по методу Дмитрия Попова (БОНУС-7):
   - ≤ 30% сирот — норма (в основном черновики и архив)
   - 30–50% — стоит предложить владельцу связать активные материалы
   - > 50% — база не связана вообще, нужна навигационная структура (карты MOC) с нуля
4. Проверить, что навигационные карты (`карта-проектов.md` и т.п.) имеют ≥ 10 входящих ссылок —
   если 0-2, картой не пользуются, это тоже находка (не файловая проблема, а проблема привычки).
5. Не удалять файлы-сироты автоматически — часть из них черновики/архив и это нормально. Находка
   тут — не список на снос, а диагноз связности + рекомендация (добавить `## Связано`, создать карту).
6. Это чужие данные (студентов) — действовать только рекомендациями, не трогать файлы без владельца
   рядом, если это не собственный vault владельца/агента.

## Зона 3 — `~/.claude/skills/`

1. `ls -la ~/.claude/skills/ | wc -l` и суммарный размер — базовая метрика на входе и на выходе.
2. Для каждого подозрительного скилла/пачки скиллов проверить признаки (все вместе — сильный сигнал,
   по отдельности — повод присмотреться):
   - **автор/домен во frontmatter SKILL.md** — не автор/freemind/известный источник
   - **единая дата установки** у большой пачки файлов, которую никто не помнит как ставили
     (`stat -c '%y %n' ~/.claude/skills/*/SKILL.md | sort` — сгруппировать по дате)
   - **отсутствие упоминания** в корневом `CLAUDE.md` (раздел «Skills — Установленные и активные»)
     и в `<системная папка>/SKILLS_CATALOG.md`
   - **тематическая несвязность** с реальными проектами владельца (например пентест/red-team пак —
     никогда не было такой задачи)
3. Проверить дубли: два скилла с пересекающимся назначением (разные имена, одна функция) —
   кандидат на слияние или архивацию менее полного.
4. Собрать список кандидатов с доказательством (grep-вывод, дата, размер) — показать владельцу ОДНИМ
   списком, не удалять по ходу проверки.
5. После подтверждения — `rm -rf` по списку, зафиксировать было→стало (кол-во файлов, МБ) в
   журнал субботников `history.md` (заводится при первом прогоне).

## Проверка сети/инфраструктуры (если с прошлого субботника менялся IP/сервер)

Урок 24.09.2026 (полная версия — `prostokvashino/references/risk-gates.md`): смена IP сервера
(даже внеплановая, типа бана РКН, не только полный переезд) может незаметно порвать несколько
систем одновременно, и это всплывает по одной проблеме за раз в разных сессиях, а не разом. Если
с прошлого субботника был инцидент со сменой IP/сервера — пройтись одним заходом: Syncthing
(completion 100%, нет relay-loop), n8n вебхуки, firewall-правила, DNS, `grep -rn "<старый-IP>"` по
проекту на забытые упоминания.

## Зона 4 — Файлы проекта (`ClaudeCode/`)

1. Найти файлы/папки не тронутые долго: `find . -type f -mtime +180 -not -path './.git/*'` как
   стартовая выборка (полгода — ориентир, не жёсткий порог).
2. Для каждого кандидата определить тип:
   - **мёртвый клон публичного репо** — можно перекачать в любой момент → удалить насовсем
   - **бэкап уже умершего проекта/бота**, задублированный в `_archive/` → удалить насовсем
   - **нетронутый шаблон** (Obsidian «Добро пожаловать» и подобное) → удалить насовсем
   - **разовый отчёт/устаревшее видение** (план миграции, отчёт аудита) → архивировать в
     `<системная папка>/archive/`, но СНАЧАЛА вынести живые незакрытые пункты в `TODO_NEXT.md` или
     канонический файл (`KNOWLEDGE_BASE.md`) — не терять хвосты вместе с архивацией
   - **дубль с идентичным содержимым другого файла** → удалить дубль сразу (паттерн чёткий)
3. **Grep на секреты** — обязательно для всего, что лежит в папках, уходящих наружу
   (`05_workshop/_publish/`, `05_workshop/_student_pack/`, что угодно раздаваемое студентам/на GitHub):
   ```bash
   grep -rEn "sk-[A-Za-z0-9_-]{10,}|api[_-]?key|AKIA[0-9A-Z]{16}|ghp_[A-Za-z0-9]{30,}|Bearer [A-Za-z0-9._-]{20,}" \
     --include='*.md' --include='*.py' --include='*.js' --include='*.json' <папка>
   ```
   Найденный ключ в раздаваемом материале — не «кандидат на обсуждение», это находка уровня
   `feedback_distributable_skill_security` — сообщать владельцу сразу, отдельной строкой, не растворять
   среди прочих файловых находок.
4. Секреты живых сервисов (не раздаваемых) — никогда не удалять, только вынести в отдельный
   gitignored файл для ручного сведения владельцем с `CREDENTIALS.md` (сам файл заблокирован для чтения
   правилом deny — не пытаться его читать/писать напрямую).
5. Итог зоны — список удалено/заархивировано/перенесено, с явным указанием куда делись живые пункты.

## Зона 5 — `<системная папка>/archive/memory_old/lessons.md` и `patterns.md`

1. Прочитать `lessons.md` целиком. Для каждого урока проверить статус:
   - подтверждён повторно? (2+ раза → кандидат в паттерн)
   - критичность высокая даже при одном повторе (безопасность, данные, деньги) → кандидат в паттерн
     сразу, без второго повторения
2. Прочитать `patterns.md`. Для каждого паттерна проверить готовность к ядру:
   - доказал пользу на нескольких кейсах?
   - не конфликтует с безопасностью?
   - нужен почти всегда, не в редких случаях?
   - формулировка короткая и однозначная (не лекция)?
   Если да по всем пунктам → кандидат «предложить в CLAUDE.md».
3. **Никогда не вносить в CLAUDE.md автоматически** — только собрать список кандидатов с
   обоснованием по каждому пункту выше и показать владельцу. Особенно строго для тем: безопасность,
   API/ключи, деньги, публичный тон/бренд, удаление данных, cron/background задачи — правило
   `self-improvement` требует явного подтверждения владельца именно по этим темам.
4. Проверить и обратный процесс — есть ли в CLAUDE.md правило, которое начало вредить/устарело →
   предложить откат в `patterns.md` с пометкой `rollback: да` и причиной (не откатывать самому).
5. Почистить сам `lessons.md`/`patterns.md` от мусора — разовых оговорок без системного смысла,
   временных хаков, вкусовых предпочтений без повторного подтверждения (это прямой критерий
   «частые ошибки» из `self-improvement» — учиться на мусоре нельзя).

## Зона 6 — Каталог Obsidian (`02_projects/`) и границы синка

Решено с владельцем 17-18.09.2026, после установки Syncthing (см. `prostokvashino` — та же
инфраструктура). Держать это в актуальном виде на каждом субботнике.

**Vault = весь `ClaudeCode/`** (не только `02_projects/`) — иначе перекрёстные ссылки на
`05_workshop/`, `01_bots/` не резолвятся (граница vault = граница папки, проверено на практике,
битая ссылка на Геракла была первым сигналом).

**Главный принцип разделения (прямая цитата смысла от владельца):** документы/переписка/мысли —
в каталог. Код, скрипты, секреты — только на сервере, работаем с ними напрямую через Claude Code.

Что входит в каталог (проверять на каждом субботнике, что состав не разъехался):
- `inbox/`, `03_club/`, `02_projects/`, `05_workshop/инструкции/`, `05_workshop/` — полностью
- `01_bots/` — ТОЛЬКО документация верхнего уровня каждой папки-бота (`CLAUDE.md`,
  `TODO_NEXT.md`, `project_STATUS.md`, `PROJECT_SKILLS.md`, `KNOWLEDGE_BASE.md` и подобные) —
  код/логи/`.claude`/`_claude`/`workflows` исключены
- `<инструменты>/`, `<системная папка>/` (там `clients/` с паролями!), `inbox/hermes/`, `99_archive/_backups/`, `screens/` —
  НИКОГДА не в каталоге, полностью исключены из синка

Проверка границы (быстрый тест на субботнике, через Syncthing REST API на сервере):
```bash
API_KEY=$(grep -oP '(?<=<apikey>)[^<]+' ~/.local/state/syncthing/config.xml)
curl -s "http://127.0.0.1:8384/rest/db/file?folder=claudecode&file=00_claude%2Fclients%2F<файл>.md" \
  -H "X-API-Key: $API_KEY"
# Пустой ответ / 404 = не в индексе = безопасно. Если вернулся JSON — секрет утёк в синк, чинить немедленно.
```

Структура каталога:
- `02_projects/README.md` — корневая карта, ссылки на все проекты/клиентов
- `02_projects/Входящие/` — сырые мысли (метод БОНУС-1), разбирать сюда попавшее на каждом субботнике
- `02_projects/<Имя клиента>/README.md` — рабочие заметки клиента (НЕ пароли — те в `<системная папка>/clients/`)
- Директор (Claude) ведёт саммари/карту сам как часть обычной работы — владелец правит вручную когда хочет

**Известный технический нюанс** (см. `prostokvashino/references/risk-gates.md` за подробностями
отладки) — .stignore-паттерны вида "запретить всё, потом разрешить (`!` после `**`)" ненадёжны в
Syncthing на практике. Рабочий способ — простой блэклист конкретных подпапок/расширений без
негации. При добавлении нового бота/агента в каталог — сверяться с этим нюансом, не наступать
повторно.

## Зона 7 — Инвентаризация и живая проверка ключей

> Дополнение 30.10.2026: проверка без вывода значений (OpenAI `/v1/models`, GitHub `/user` + scopes) и поиск,
> где ключ используется перед отзывом (конфиги, git remotes, n8n `workflow_entity`, `export:credentials --decrypted` → счётчик) —

Введена по итогам первого субботника (05-06.10.2026): находки живых/мёртвых ключей всплывали сразу
в трёх разных зонах (1, 3, 4) порознь — выделена в отдельный штатный шаг, чтобы не зависеть от
того, в какой зоне ключ случайно всплывёт. Алгоритм — ровно тот, что реально прогонялся 06.10.2026.

1. **Собрать полный список** уникальных значений ключей/токенов из всех источников разом, не по одному:
   - `<системная папка>/CREDENTIALS.md` (канонический, но может быть устаревшим — это и проверяем)
   - `<системная папка>/KEYS_TO_MERGE_*.md` (если есть незавершённые от прошлых сверок)
   - реальные рабочие файлы: `~/.env`, `~/.hermes/.env`, `~/.hermes/profiles/*/.env`,
     `<инструменты>/.env` (и другие локальные `.env`, если заведутся — они имеют свойство расходиться
     с `~/.env`, см. прецедент `provod_digest.py` ниже)
   - grep по всему `~/YandexSync/ClaudeCode/` на паттерны: `sk-`, `Bearer `, `API_KEY=`, `pza_`,
     `csk-`, `key_`, `ghp_`, `tgp_v1`, `AKIA[0-9A-Z]{16}`, Telegram bot-token
     `\d{8,10}:[A-Za-z0-9_-]{35}`
   - Дедуп по ЗНАЧЕНИЮ, не по месту встречи — один ключ может лежать в 4-5 файлах сразу (прецедент:
     один OpenAI-ключ нашёлся в 4 местах, один OmniRoute-ключ — в 3).

2. **Прогнать каждое уникальное значение живым запросом** к соответствующему API (не доверять
   пометкам в документации на слово — они устаревают, прецедент: Together и Anthropic были
   задокументированы как мёртвые, оказались живыми; OmniRoute считался «скорее мёртвым», оказался
   рабочим):
   ```bash
   # OpenAI
   curl -s -o /dev/null -w "%{http_code}" https://api.openai.com/v1/models -H "Authorization: Bearer $KEY"
   # Anthropic — версия заголовка обязательна, без неё 400 даже у живого ключа
   curl -s -o /dev/null -w "%{http_code}" https://api.anthropic.com/v1/models -H "x-api-key: $KEY" -H "anthropic-version: 2023-06-01"
   # OpenRouter
   curl -s -o /dev/null -w "%{http_code}" https://openrouter.ai/api/v1/key -H "Authorization: Bearer $KEY"
   # Cerebras / Together / Polza — OpenAI-совместимые, одинаковый паттерн
   curl -s -o /dev/null -w "%{http_code}" https://api.cerebras.ai/v1/models -H "Authorization: Bearer $KEY"
   curl -s -o /dev/null -w "%{http_code}" https://api.together.xyz/v1/models -H "Authorization: Bearer $KEY"
   curl -s -o /dev/null -w "%{http_code}" https://api.polza.ai/v1/models -H "Authorization: Bearer $KEY"
   # Telegram-бот
   curl -s "https://api.telegram.org/bot$TOKEN/getMe"
   # SkillsMP
   curl -s -o /dev/null -w "%{http_code}" "https://skillsmp.com/api/v1/skills/search?q=test" -H "Authorization: Bearer $KEY"
   # OmniRoute (локальный сервис, может быть выключен — см. п.5)
   curl -s -m 10 http://localhost:20128/v1/models -H "Authorization: Bearer $KEY"
   ```
   200/живой ответ = жив. 401/403/429(credit_balance) = мёртв или без баланса — отметить разницу
   (мёртвый ключ ≠ живой ключ без денег, второй можно пополнить, не ротировать).

3. **Собрать единый список** (статус, где реально используется — `.env`/конфиг, где просто лежит
   в документах) и этим же проходом **поправить `CREDENTIALS.md`** — убрать противоречия
   (устаревшие пометки «мёртв»/«жив»), указать дату проверки (сегодняшнюю, не выдуманную).

4. **Почистить безопасно, без ожидания ротации:**
   - Подтверждённо мёртвые значения — вычистить из файлов сразу, ротация не нужна.
   - Дубли одного и того же значения в нескольких файлах — свести к одному канону + env-ссылкам
     из кода (прецедент: ключ хардкожен в `.py`-скрипте — заменить на `os.environ`, и
     **обязательно протестировать скрипт живым запуском после правки**, не вслепую).
   - Разошедшиеся локальные `.env`-файлы (не канонический `~/.env`) — синхронизировать,
     проверить какой скрипт их реально читает (`grep os.environ\|os.getenv`), протестировать.

5. **Живые ключи, раздаваемые/публично зашитые** (студенческие паки, установленные скиллы) —
   эскалировать сразу (см. Зону 4 п.3), но ПЕРЕД тем как чистить текст — проверить, можно ли
   перевыпустить ключ БЕЗ владельца: если сервис свой/самохостед (пример — OmniRoute, свой дашборд на
   `localhost`) — ключ можно перевыпустить и заменить самостоятельно, это не требует логина на
   чужой сайт. Если сервис внешний (OpenAI/Anthropic/OpenRouter и т.п.) — ротация только через
   аккаунт владельца, это НЕ входит в полномочия субботника, только фиксация + эскалация в
   `РОТАЦИЯ_КЛЮЧЕЙ_*.md`.

6. Не печатать ПОЛНЫЕ значения ключей в отчёт — только маска (первые 8-10 + последние 4 символа) и
   статус.
