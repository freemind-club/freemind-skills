# Гейты подтверждения — действия, требующие отдельного явного «да»

> Принцип из `feedback_ask_before_execute`: без отлаженного протокола — сначала все вопросы, потом
> действие; не заполнять пробелы предположениями. Перед широким/необратимым действием — просить
> проверяемое доказательство (вывод команды, лог, статус), не словесное подтверждение. Переезд —
> задача без отлаженного протокола (в отличие от постов, где пайплайн уже обкатан), поэтому здесь
> этот принцип строже, чем где-либо ещё в системе.

**Общее правило:** одно общее «да, переезжай» / «начинай переезд» НЕ покрывает ни один из пунктов
ниже. На каждый — своё отдельное явное подтверждение владельца, в момент когда до него дошла очередь,
не заранее оптом.

## 0. 🔒 Гейт полноты дампов — «задамплены ВСЕ инстансы БД» (перед Шагом 3)

**Почему отдельный гейт:** в бою 27.10.2026 дампы «всех баз» оказались дампами 3 инстансов из 5.
Пропущены хостовый Postgres (главная база, не в Docker) и контейнер без compose. Слово «задамплено»
без сверки ничего не значит.

**Правило именования дампов:** один файл на инстанс, имя начинается с идентификатора инстанса и
точки или подчёркивания:
- Docker: `<имя-контейнера>.sql.gz` или `<имя-контейнера>_<дата>.sql.gz` (`docker exec <c> pg_dumpall -U <user> | gzip`);
- хостовый Postgres: `host-pg<версия>.sql.gz` для кластера `main`, иначе `host-pg<версия>-<кластер>.sql.gz`
  (`sudo -u postgres pg_dumpall -p <порт> | gzip`);
- висячий docker volume с данными СУБД: `volume_<имя-volume>.tar.gz` (архив каталога volume) или
  `volume_<имя-volume>.sql.gz` (дамп через временный контейнер той же версии СУБД);
- stderr дампа — рядом в `<то же имя>.err`. Непустой `.err` означает, что дамп под вопросом.

**Решение «не нужен»** для висячего volume записывается в `<папка-дампов>/DECISIONS.tsv`, одна строка
на volume, поля через TAB: `volume_<имя>	НЕ ПЕРЕНОСИМ	<кто и когда решил, причина>`. Пишет её
директор после ответа владельца, не агент по своей догадке.

**Команда-доказательство** (только читает, временных файлов не создаёт; сырой вывод показать владельцу).
Сверяет инстансы с дампами, **базы в дампе с живыми базами** (без служебной `postgres`) и висячие
volume с данными СУБД. Строку «ГЕЙТ ПРОЙДЕН» печатает, только если нет ни MISSING, ни расхождения
баз, ни volume без решения:

```bash
DUMPS=~/backups/<папка-дампов>
Q='select datname from pg_database where not datistemplate and datname <> current_database() order by 1'
INST=$( { pg_lsclusters -h 2>/dev/null | awk '{print "host-pg"$1 ($2=="main" ? "" : "-"$2) "\thost "$3}'
  docker ps -a --format '{{.Names}}\t{{.Image}}' \
    | awk -F'\t' 'tolower($2) ~ /postgres|pgvector|mysql|mariadb|mongo/ {print $1"\tdocker "$2}'
} | sort -u )
echo "== Инстансы СУБД: $(printf '%s\n' "$INST" | command grep -c .)"; printf '%s\n' "$INST"
echo "== Слушающие порты СУБД (каждый должен соответствовать строке выше)"
ss -tlnpH | command grep -E ':(543[0-9]|3306|3307|27017)\b' | awk '{print $4, $6}'
echo "== Хостовые юниты СУБД"
systemctl list-units --all --no-legend | command grep -iE 'postgres|mysql|mariadb|mongo' | awk '{print $1, $3, $4}'
live_dbs() {  # $1 = имя инстанса, $2 = тип (host <порт> | docker <образ>)
  case "$2" in
    host*) (cd / && sudo -u postgres psql -p "${2#host }" -d postgres -Atc "$Q" 2>/dev/null) ;;
    docker*postgres*|docker*pgvector*) docker exec -e Q="$Q" "$1" sh -c 'U="${POSTGRES_USER:-postgres}"
      psql -U "$U" -d postgres -Atc "$Q" 2>/dev/null ||
      PGPASSWORD="$POSTGRES_PASSWORD" psql -h 127.0.0.1 -U "$U" -d postgres -Atc "$Q" 2>/dev/null' ;;
  esac | tr '\n' ' ' | sed 's/ $//'; }
echo "== Сверка с дампами в $DUMPS (служебная база postgres не считается)"
miss=0
while IFS=$'\t' read -r name kind; do
  [ -z "$name" ] && continue
  f=$(ls -1 "$DUMPS" 2>/dev/null | awk -v n="$name" '(index($0,n".")==1 || index($0,n"_")==1) && /\.(sql|sql\.gz|dump|gz|zst)$/' | head -1)
  if [ -n "$f" ] && [ -s "$DUMPS/$f" ]; then
    e="$DUMPS/${f%%.*}.err"; [ -s "$e" ] && w=" ⚠️ непустой .err" || w=""
    d=$(zcat -f "$DUMPS/$f" 2>/dev/null | command grep -oE '^CREATE DATABASE [^ ;]+' | awk '{print $3}' | sort | tr '\n' ' ' | sed 's/ $//')
    l=$(live_dbs "$name" "$kind")
    if [ -z "$l" ]; then c="живые: не прочитать (остановлен/не PG) — сверить с описью §5"
    elif [ "$l" = "$d" ]; then c="живые = дамп"
    else c="❌ живые [$l] ≠ дамп"; miss=$((miss+1)); fi
    echo "OK      $name -> $f ($(du -hL "$DUMPS/$f" | cut -f1); в дампе: [$d]; $c)$w"
  else echo "MISSING $name"; miss=$((miss+1)); fi
done <<< "$INST"
echo "== Висячие docker volume с данными СУБД (ни один контейнер их не использует)"
und=0
for v in $(docker volume ls -qf dangling=true); do
  m=$(docker volume inspect -f '{{.Mountpoint}}' "$v")
  k=$(find "$m" -maxdepth 2 \( -name PG_VERSION -o -name ibdata1 -o -name WiredTiger \) -printf '%P ' 2>/dev/null | sed 's/ $//')
  [ -z "$k" ] && continue
  a=$(ls -1 "$DUMPS" 2>/dev/null | awk -v n="volume_$v" 'index($0,n".")==1' | head -1)
  r=$(awk -F'\t' -v n="volume_$v" '$1==n {print $2" — "$3}' "$DUMPS/DECISIONS.tsv" 2>/dev/null | head -1)
  if [ -n "$a" ] && [ -s "$DUMPS/$a" ]; then echo "OK      volume $v ($(du -sh "$m" | cut -f1), $k) -> $a ($(du -hL "$DUMPS/$a" | cut -f1))"
  elif [ -n "$r" ]; then echo "РЕШЕНО  volume $v ($(du -sh "$m" | cut -f1), $k): $r"
  else echo "НЕТ РЕШЕНИЯ volume $v ($(du -sh "$m" | cut -f1), $k)"; und=$((und+1)); fi
done
echo "== MISSING: $miss  | volume без решения: $und"
[ "$miss" -eq 0 ] && [ "$und" -eq 0 ] && echo "ГЕЙТ ПРОЙДЕН (порты/юниты сверь глазами)" || echo "ГЕЙТ НЕ ПРОЙДЕН"
```

Проверено 27.10.2026 на боевом сервере: 5/5 инстансов, базы «живые = дамп» везде, volume
`freemind_ai_intensive_pgdata` → архив. Без архива и без строки в `DECISIONS.tsv` тот же скрипт
печатает `НЕТ РЕШЕНИЯ volume …` и `ГЕЙТ НЕ ПРОЙДЕН` (в 0.2.0 он писал «ПРОЙДЕН»).

**Условия прохождения (все три):**
1. `MISSING: 0` и `volume без решения: 0`.
2. Каждый слушающий порт СУБД из `ss` и каждый хостовый юнит соответствует строке в списке
   инстансов. Порт, который держит не `docker-proxy` и не кластер из `pg_lsclusters` (например,
   MySQL или Postgres, собранный руками), значит, что инстанс не учтён. Его надо добавить в список и
   задампить.
3. Базы в каждом дампе (`CREATE DATABASE`) совпадают с живыми базами инстанса без служебной
   `postgres` (`pg_dumpall` её не создаёт, поэтому дамп всегда «на одну меньше» полного списка). Для
   остановленного контейнера скрипт живые базы не прочитает — сверить с описью §5 руками.

Что гейт **не** считает: Redis и прочие кэши/очереди (решение по ним — в плане, см. опись §5),
MySQL/Mongo без Postgres-клиента (для них строка OK по файлу, базы сверять руками).

Без 100% совпадения к Шагу 3 не переходить. Перед финальным дампом в окне простоя гейт проходится
повторно.

## 1. Force-push после `git filter-repo` / BFG

**Почему отдельный гейт:** переписывает историю репозитория необратимо для всех, у кого есть
клон. Любой, кто не переклонирует, окажется с расходящейся историей и либо потеряет локальные
изменения при `pull`, либо намусорит конфликтами. Затрагивает все
устройства с клоном одновременно.

**Что просить перед выполнением:** явное «да, делай force-push» именно на этот шаг, отдельно от
согласия на сам переезд. После push — сразу сообщить, что старые локальные копии на всех устройствах
теперь невалидны и требуют переклонирования, не полагаться что это "само собой понятно".

## 2. Удаление чего-либо на СТАРОМ сервере

**Почему отдельный гейт:** старый сервер после переезда выключается — это и есть та самая
необратимость, ради которой существует весь этот скилл. Удаление на старом сервере до
подтверждённой работы нового — самый вероятный сценарий безвозвратной потери.

**Что просить перед выполнением:** зелёный результат ПОЛНОГО блока проверки из
`checklist.md` §5 (все сервисы с меткой ПЕРЕНОСИМ, БД, Claude Code, сайты) — показать владельцу
проверяемый вывод команд/статусов, не пересказ "вроде всё работает". Только после этого — явное
«да, выключай/удаляй старое».

## 3. Отзыв старых ключей и токенов

**Почему отдельный гейт:** необратимо и может сломать что-то незамеченное, что всё ещё использует
старый ключ (забытый воркфлоу, скрипт на другом сервере). Статус выполнения этих пунктов уже был
неопределённым в чек-листе субботника — **не предполагать, что раз пункт старый, значит уже
сделан или уже неважен**.

**Что просить перед выполнением:** сначала проверить, не сделано ли уже (спросить/проверить в
кабинете провайдера), затем явное «да, отзывай» на каждый ключ отдельно: три ключа — три
отдельных действия, не один пункт.

## 4. Переключение DNS / доменов на новый IP

**Почему отдельный гейт:** если сделано раньше времени (до готовности нового сервера) —
внешний трафик, боты, webhooks идут в никуда, пока новый сервер не поднят полностью. Если сделано
слишком поздно — путаница, какой сервер сейчас "боевой".

**Что просить перед выполнением:** подтверждение, что весь блок `checklist.md` §5 зелёный, плюс
явное «да, переключай DNS».

## 5. Консолидация Postgres-баз (слияние нескольких БД в одну)

**Почему отдельный гейт:** необратимая структурная операция над данными — не просто перенос
файла, а изменение схемы/расположения. Ошибка в консолидации может смешать или потерять данные
разных проектов (клиенты, LightRAG-графы, n8n-состояния).

**Что просить перед выполнением:** `pg_dump` каждой исходной базы ДО консолидации (см.
`feedback_backup_before_agent` — принцип «сначала дамп, потом трогать»), затем явное решение
владельца, какие базы консолидировать, а какие нет — не решать самостоятельно, если план неочевиден
(см. открытые вопросы в `checklist.md`). Одноимённые базы в разных инстансах (в бою: две `oleg_brain`)
— сначала выяснить, какая боевая.

## 6. Заявление «новый шлюз/провайдер готов, риск минимальный»

**Почему отдельный гейт:** не удаление и не необратимое действие само по себе, но прецедент
(`feedback_check_quotas_before_promising`) показал, что необоснованное «риск минимальный» ведёт к
поспешным следующим необратимым шагам (например — к преждевременному отключению старого шлюза).

**Что просить перед тем как объявить готовым:** реальный burst-тест лимитов каждого
провайдера нового шлюза (не чтение документации), показать владельцу результат теста, а не вывод
"настроено, должно работать".

## Что НЕ требует отдельного гейта

Обычные, обратимые на этом этапе действия — не нужно останавливаться на каждый шаг:
- Чтение/копирование со старого сервера (не изменяет и не удаляет ничего на старом)
- `pg_dump` (создание дампа — не изменяет исходную БД)
- Поднятие сервисов на НОВОМ сервере (пока старый жив и работает как раньше — можно откатиться)
- Тестовые запросы к новым провайдерам/сервисам, не затрагивающие прод-данные

Разница простая: если действие можно отменить, просто не выполняя следующий шаг — гейт не нужен,
достаточно обычного рабочего темпа. Если действие само по себе необратимо или закрывает путь назад
— гейт обязателен.

## Урок 24.09.2026 — смена IP/сервера ломает системы незаметно, проверять ВСЕ разом

**Что произошло (прецедент):** сервер сменил IP (<СТАРЫЙ_IP> → <ТЕКУЩИЙ_IP>, бан РКН за WireGuard
23.09). Синхронизация Syncthing между сервером и Mac стала нестабильной (соединение рвётся каждые
10-15 мин через relay) — не факт, что это прямое следствие смены IP (Syncthing не привязан к
статическому IP, у него device-ID + discovery), но совпадение по времени подозрительное, и владелец
сам не сразу вспомнил, что IP вообще менялся — заметил проблему в синке раньше, чем связал её с
переездом IP.

**Урок:** при смене сервера/IP (даже частичной — не полный переезд, а просто новый внешний адрес)
проверять ВСЕ завязанные на сеть системы одним проходом, не дожидаясь пока проблема всплывёт по
одной за раз в разных сессиях:
- Syncthing (все устройства reconnected, completion 100%, нет затяжных relay-loop)
- n8n (вебхуки, если завязаны на прежний IP/домен в конфиге)
- Firewall/ufw — правила применились к новому IP, ничего не заблокировано неожиданно
- DNS-записи, если домены указывали на старый IP
- Любые hardcoded IP в конфигах/скриптах (`command grep -rn "<старый-IP>"` по всему проекту — быстрый
  способ найти забытые упоминания)

**Применять и без полного переезда** — при любой внеплановой смене IP (например, бан РКН): пройтись по этому списку сразу
после события, не через несколько дней когда пользователь сам заметит что-то отвалившееся.
