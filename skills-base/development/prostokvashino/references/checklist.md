# Чек-лист переезда — универсальный

> Конкретику (откуда, куда, железо, даты, бюджет, что не везём) здесь не держать. Она живёт в плане
> `<системная папка>/logs/migration/PLAN_<откуда>_to_<куда>_<YYYY-MM>.md`. Этот файл задаёт порядок и типовые
> пункты. Пункты с пометкой **«если есть»** выполняются, только если сервис реально найден в описи
> или явно включён в план.

## 0. План переезда — шаблон файла

Создать до Шага 1 и обновлять по ходу:

```
# План переезда <откуда> → <куда> — <YYYY-MM>
## Откуда / Куда        — провайдер, ресурсы, ОС, IP (если известен), регион
## Рамки                — что НЕ переносим и почему; бюджет; что сознательно НЕ меняем вместе с переездом
## Источник фактов      — `<системная папка>/logs/migration/INVENTORY_<дата>.md
## Решения владельца        — ответы на СПРОСИТЬ из описи (номер → решение)
## Порядок и окно простоя — когда стоп пишущих, финальный дамп, DNS, проверка
## Риски                — из §0 описи
## Статус               — какой шаг скилла сейчас
```

## 1. Инвентаризация и сверка (Шаги 1-2 скилла)

- [ ] Опись по `inventory-template.md` → `<системная папка>/logs/migration/INVENTORY_<дата>.md`
- [ ] Сверка опись ↔ план: чего нет на сервере, чего нет в плане
- [ ] Все СПРОСИТЬ закрыты ответами владельца и записаны в план
- [ ] Решено, когда чистить мёртвое (кандидаты для Геракла): ДО переезда или ПОСЛЕ

## 2. Базы данных — дамп КАЖДОГО инстанса

> «Сначала дамп, потом трогать» (прецедент: снос 418 контактов без бэкапа). Один общий бэкап «на
> всё» не считается.

- [ ] Таблица инстансов из описи §5 (хост + Docker, включая контейнеры без compose и висячие volume)
- [ ] Дамп каждого инстанса по правилу именования из `risk-gates.md` §0
      (хост: `pg_dumpall` от postgres; Docker: `docker exec <c> pg_dumpall -U <user>`)
- [ ] **🔒 Гейт `risk-gates.md` §0 пройден**: 0 строк MISSING, сырой вывод показан владельцу
- [ ] Консолидация баз только по решению владельца и только после гейта (`risk-gates.md` §5).
      Одноимённые базы в разных инстансах — сначала выяснить, какая боевая.

## 3. Окно простоя и перенос (Шаг 3 скилла)

- [ ] Окно согласовано с владельцем (время, что лежит, сколько)
- [ ] Остановлены пишущие в БД: n8n, боты, агенты с cron. Иначе данные между финальным дампом и
      переключением DNS разойдутся
- [ ] Финальный дамп всех инстансов, повторный гейт §0
- [ ] Репозиторий переносится **rsync целиком** (`rsync -aHAX --info=progress2`), а не `git clone`,
      если в описи много gitignored-данных. Путь на новом сервере тот же
- [ ] Секреты и конфиги переносятся файлами по SSH/rsync, не через git и не через Syncthing
- [ ] Ключ шифрования n8n перенесён (иначе credentials n8n не расшифруются)
- [ ] Статика `/var/www/*` и конфиги веб-сервера перенесены
- [ ] Контейнеры без compose или с мёртвым путём: на новом сервере для них написан compose-файл
      (параметры из `docker inspect` в описи)
- [ ] Docker-порты биндятся на `127.0.0.1`, наружу только через reverse proxy. ufw: только нужное
- [ ] Захардкоженные IP из описи §7 заменены на `localhost`/домен
- [ ] Пароли из командных строк процессов перенесены в env или файлы (риск из описи)

## 4. Поднять на новом сервере — типовые блоки

**База:** docker + compose, ufw, earlyoom (если был), веб-сервер (nginx или Caddy), certbot, СУБД.

**Сервисы:** всё с меткой ПЕРЕНОСИМ из описи §2-3 (system и user-юниты, включая таймеры и их
скрипты в `/usr/local/bin`). Для user-юнитов: `loginctl enable-linger <user>`.

**Рантайм:** те же версии node (nvm), uv tools, pipx, браузер для playwright. Где версия вшита
абсолютным путём (хуки, MCP, PATH юнитов), поставить ту же версию или поправить пути.

**Claude Code:**
- [ ] CLI установлен (та же node-версия, если пути вшиты)
- [ ] `~/.claude/` перенесён: skills, hooks, settings.json, plugins, `projects/<slug>/memory/`
- [ ] `~/.claude.json` и `.credentials.json` перенесены (или перелогиниться)
- [ ] Путь репо совпадает со старым (slug памяти)

**Опциональные блоки — «если есть» в описи или в плане:**
- [ ] *Если есть* Гермес: `~/.hermes` (без cache/tools, если решено пересобрать), установка той же
      версии agent'а (не копия venv), профили, cron `jobs.json`, MCP-бинарники
- [ ] *Если есть* LightRAG (один или несколько инстансов): compose + `.env` + дамп Postgres
- [ ] *Если есть* Ollama: модели перекачать, облачный ключ перенести файлом
- [ ] *Если есть* Syncthing: поставить заново, новый Device ID, переподключить клиентские устройства
      (см. `syncthing-technical-notes.md`). Полный перенос стека делать НЕ через Syncthing: `.stignore`
      общий и узкий, он отдаст только подмножество файлов. Порядок: rsync → сервер рабочий →
      Syncthing → отключение старого от папки
- [ ] *Если есть* VPN (WireGuard/wg-easy/3X-UI и т.п.): переносить только по решению в плане
- [ ] *Если в плане* новый шлюз моделей (LiteLLM или аналог): **отдельный проект, не совмещать с
      переездом**, иначе меняются две переменные сразу. Если всё же вместе, то burst-тест лимитов
      каждого провайдера до заявления «готово» (`risk-gates.md` §6)
- [ ] *Если в плане* чистка git-истории (`git filter-repo`/BFG): force-push только через гейт
      `risk-gates.md` §1, после него переклонировать на всех устройствах

## 5. Проверка после переезда (гейт перед Шагом 5)

Каждый пункт подтверждается выводом команды, а не пересказом:

- [ ] Все сервисы с меткой ПЕРЕНОСИМ active (`systemctl` / `systemctl --user` / `docker ps`)
- [ ] БД: число баз и ключевые счётчики строк совпадают со старым сервером
- [ ] n8n: credentials расшифровываются, активные воркфлоу (список из описи) живы, тестовый webhook проходит
- [ ] Боты отвечают в тестовом чате
- [ ] LightRAG (каждый инстанс): health + тестовый `query_text`
- [ ] Гермес (если есть): отвечает, cron-задачи на месте
- [ ] Сайты и статика: `curl -I` по каждому домену после смены DNS, сертификаты валидны
- [ ] Claude Code: сессия стартует, SessionStart-хук отрабатывает, все MCP подключаются
- [ ] Захардкоженные IP: повторный grep из описи §7 пуст по старому IP
- [ ] Порты снаружи: с другой машины проверить, что открыты только нужные (`nmap` или онлайн-сканер)
- [ ] Syncthing (если есть): клиенты подключены, completion 100%

## 6. Удаление старого — ТОЛЬКО после зелёного §5

Отдельное «да» на каждый пункт (`risk-gates.md`):

- [ ] Переключение DNS (если не сделано в §3): `risk-gates.md` §4
- [ ] Отзыв старых ключей и токенов из плана: проверить, не отозваны ли уже. Каждый ключ отдельным «да»
- [ ] Финальный архив со старого сервера (то, что НЕ ПЕРЕНОСИМ, но «на всякий случай») скачан и проверен
- [ ] Выключение или удаление старого сервера: `risk-gates.md` §2
