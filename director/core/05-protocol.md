## ФИНАЛ

> **Сохранение выводов в память — обязательная часть финала.** Push в git — **нет.**
> Память фиксирует, *почему* так сделали, какие паттерны и уроки — это теряется после сессии, если не записать. А git-push — это публикация коммитов во внешний репозиторий, и она делается только когда пользователь этого хочет и сказал «да».

1. Обновить статус проекта / TODO / журнал ({{STATUS_FILES}})
2. **Разбор диалога → паттерны и выводы, не пересказ действий.** Вытащить: какие решения приняли и почему · что оказалось рабочим паттерном · какие косяки → правила (см. [04-improvement.md](04-improvement.md)) · с чем это связано в других проектах. «Сделал X, потом Y» — не вывод.
3. Свериться с памятью (`MEMORY.md` + штатная память среды) — что уже есть, не дублировать.
4. Показать {{USER_NAME}} список: **что + зачем** записать/обновить. Прогнать список через принцип 7 (нет ли там чувствительного).
5. Дождаться ОК → записать. Показать сырой результат (не «записал»).

**Git — только если работа велась в репозитории И пользователь просил зафиксировать (или заранее согласовал такой режим для проекта):**

6. `git add` **конкретные файлы** (никогда `git add -A` / `git add .`).
7. **Показать пользователю:** remote (`git remote -v`), ветку, список коммитов и файлов. Прогон на секреты (`.env`, `API_KEY`, `PASSWORD`, `_KEY=`, `TOKEN` в добавленных файлах) — нашёл → стоп, спросить.
8. **Спросить явно: «Запушить это в <remote> <ветка>? [да/нет]».** Без «да, отправляй» — **не пушить**, оставить коммит локально. Force-push — отдельное усиленное подтверждение, по умолчанию запрещён.
9. После «да» → commit (если ещё не) → `git pull --rebase` при отказе → push. Подтвердить: «Записал в память; запушил <ветка> <хэш>: <файлы>» (или «коммит локальный, не пушил — ждёшь?»).

**Если репозитория нет и пользователь хочет сохранять историю** — предложить `git init` + приватный remote. Не навязывать.

## Длинные задачи и переполнение контекста

Долгая сессия / большая задача (Hermes-цепочка, разбор кучи файлов) → следить за объёмом контекста. Скилл `context-lifecycle` (пороги 55/70/85%, handoff), если установлен.

- ~70% → зафиксировать состояние в память (что сделано, что осталось, активный план) и в статус проекта.
- ~85% → handoff: короткое резюме (не пересказ диалога — рабочее состояние: план, что изменено, что дальше, открытые ОК) → продолжить с чистого контекста.
- После компакта/handoff — **перечитать** `SKILL.md` + `references/` + активный план: правила и план не должны потеряться.

## Pre-Project Protocol (перед стартом крупного проекта)

1. Выбрать модели под задачу → ping-test, что живы
2. Проверить `~/.claude/skills/` — какие скиллы подходят под задачу
3. Новые скиллы → провалидировать (`skill-creator`, `skill-conductor`) → записать в `PROJECT_SKILLS.md` проекта
4. Нужен мультиагент? → `agent-team-orchestration`
5. Только потом — разработка
