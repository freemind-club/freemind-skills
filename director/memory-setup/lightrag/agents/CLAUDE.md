# CRITICAL — READ FIRST

## Перед первым использованием — согласие пользователя

LightRAG — это внешнее хранилище, отдельное от этого чата: чаще всего сервис на сервере (свой Docker-контейнер, локально или на VPS), а не встроенная память агента. Прежде чем этим файлом начинают руководствоваться, пользователь должен явно подтвердить, что:

1. Знает, **где физически стоит LightRAG** (свой сервер / чужой VPS / localhost) — это должно быть сказано ему прямо при установке, не молчаливым фактом.
2. Согласен, что часть переписки и рабочих фактов будет туда сохраняться.
3. Понимает, что может **посмотреть, экспортировать и удалить** сохранённое в любой момент (см. «Управление памятью» ниже).

Без этого согласия — работать на файловой памяти (`memory/MEMORY.md` и т.п.), LightRAG не подключать. Это не хуже — это нормальный, поддерживаемый вариант, не «урезанный».

## ⚠️ MANDATORY FIRST ACTION — LightRAG Knowledge Base

Если LightRAG подключён и согласие получено — **перед тем как отвечать, сначала прочитай контекст.**

1. Возьми первое сообщение пользователя в сессии
2. Вызови MCP `query_text`, mode `hybrid`, с релевантным запросом
3. Используй результат, чтобы ответить точнее
4. Само обращение к базе пользователю не озвучивать — это техническая деталь, а не секрет

Это только ЧТЕНИЕ — не создаёт новых рисков сверх уже данного согласия.

## Что можно сохранять, а что нельзя

**Можно (по умолчанию):** технические решения, выбор инструментов, договорённости о процессе, факты о проекте, найденные и решённые баги.

**Нельзя без отдельного явного разрешения пользователя на КАЖДЫЙ такой случай:**
- медицинские данные, диагнозы, состояние здоровья (свои или третьих лиц)
- данные клиентов/пациентов пользователя — имена, истории, переписка с ними
- пароли, ключи, токены, номера карт, документы, удостоверяющие личность
- содержимое чужой переписки, пересланной пользователем (это чужие данные, не его)

Если сомневаешься, относится ли факт к этим категориям — **не сохраняй**, спроси.

## Во время работы

Значимое решение, предпочтение, факт о проекте — сохраняй через `insert_text`, но не любой ценой и не бездумно: одно решение = одна запись, не пересказ диалога.

**Сохраняй:** архитектурные решения, выбор технологий, предпочтения, факты о проекте, решённые баги.
**Не сохраняй:** опечатки, промежуточную отладку, разовые мелкие просьбы, дубли, временные значения — и всё из списка запретов выше.

**Формат:** 1-3 предложения. Указывай проект и причину, если применимо.

### Явные команды

- **«запомни/запиши <текст>»** → сохранить через `insert_text` (кроме категорий из списка запретов — предупредить и уточнить)
- **«вспомни/найди в базе знаний <тема>»** → найти через `query_text` (hybrid), показать результат

## Управление памятью

Пользователь в любой момент может попросить:
- **показать**, что сохранено по теме — `query_text`, вывести как есть
- **удалить** конкретную запись — если инструмент MCP поддерживает удаление; если нет — сказать прямо, что удаление сейчас недоступно, не делать вид, что сделано
- **экспортировать** — выгрузить найденное текстом в файл

## Автозапись «сохраняй всё» — с осторожностью

Если пользователь прямо просит «записывай сюда всё» / «save everything here»:
1. Прежде чем начать — напомнить одной строкой, что это значит **каждое** его сообщение, включая случайно упомянутое личное, и спросить подтверждение именно на это ("да, всё" / "нет, отмена")
2. Только после да — вставлять каждое сообщение пользователя через `insert_text`, формат: `"[YYYY-MM-DD] Автор: полный текст"`
3. Включать цитируемый/пересланный контекст, если есть — но помнить, что это может быть чужая переписка (см. запреты выше)
4. Свои ответы и системные сообщения не сохранять

Остановить: пользователь говорит «хватит записывать» или аналогично.
